# 定常運用・データ再処理・モデル更新

更新日: 2026-08-13

## 1. 現在の運用単位

現在のシステムは、次の4系統に分かれる。

| 系統 | 役割 | 現在の状態 |
|---|---|---|
| 日次データ・Rule Rank | 外部取得、特徴量、品質検査、画面公開 | 定時ジョブで実行。LLMは使わない |
| 日次レポート | 最新特徴量へモデル推論し、PDF・JSONをOneDriveへ保存 | 日次処理成功後に自動実行 |
| 過去データ・LLM | 財務・株価バックフィル、TDnet原文、LLM構造化 | コマンド実装済み、手動または必要時のみ |
| 学習モデル | 月次学習表、Ridge学習、期間外評価、比較・評価タブ | コマンド実装済み、スケジュール未登録 |

メイン画面の正式順位は`rule_rank_v6_unadjusted_valuation`である。Ridgeは改善候補を比較する
Challengerであり、メイン順位を自動的に置き換えない。

## 2. 推奨スケジュール

| 頻度 | 処理 | 自動化 | 主コマンド |
|---|---|---|---|
| 毎日19:30 | データ取得、Rule Rank、品質検査、公開、日次PDF保存 | 登録スクリプト実装済み | `run-daily.sh` |
| 毎週日曜20:30 | DuckDBバックアップ | 登録スクリプト実装済み | `asset-poc backup` |
| 週次または必要時 | TDnet原文を必要に応じて手動でLLM構造化し、補助特徴量として評価 | 手動 | `structure-disclosures` → `publish` |
| 月次 | Point-in-Time学習表を再構築し、6M/12Mを再学習 | 手動 | `build-training-dataset` → `train-model` |
| 四半期 | Challengerと現行Rule Rankを比較し、改善採否をレビュー | 手動 | `evaluate-model` |
| 半期またはUniverse変更時 | 新規銘柄の価格・財務履歴、Universe充足を監査 | 手動 | `collect-yahoo`、`backfill-financials` |

学習を毎日行う必要はない。価格・決算は日次で蓄積するが、評価日は月次で、6M/12Mラベルが
確定する速度も遅いため、再学習は月次、モデル入れ替え判断は四半期で十分である。

タスク登録用スクリプトは実装済みである。2026-08-13の照会では、Windows側の`AssetAIAdviser-Daily`と`AssetAIAdviser-Backup`は未登録だったため、現時点では自動起動しない。

```powershell
cd C:\path\to\asset-ai-adviser\poc
powershell -ExecutionPolicy Bypass -File .\scripts\register-tasks.ps1
Get-ScheduledTask -TaskName "AssetAIAdviser-*"
```

登録後は`AssetAIAdviser-Daily`と`AssetAIAdviser-Backup`が表示される。PC停止・スリープ中に
予定時刻を過ぎた場合は、`StartWhenAvailable`により復帰後に起動する。

### OneDriveへの日次モデルランキング

日次タスクは次のフォルダを既定の出力先とする。

```text
ユーザー環境の同期フォルダ（REPORT_OUTPUT_DIRで設定）
```

変更する場合は`poc/.env`へ`REPORT_OUTPUT_DIR`を設定するか、
`daily-report --report-dir PATH`で実行時に指定する。実行時指定が最優先である。

`asset-poc daily-report`は次を保存する。

```text
output/pdf/daily/YYYY/MM/asset-ai-model-ranking-YYYYMMDD.pdf
output/pdf/daily/YYYY/MM/asset-ai-model-ranking-YYYYMMDD.json
out_report/asset-ai-model-ranking-latest.pdf
out_report/asset-ai-model-ranking-latest.json
out_report/archive/YYYY/MM/asset-ai-model-ranking-YYYYMMDD.pdf
out_report/archive/YYYY/MM/asset-ai-model-ranking-YYYYMMDD.json
```

PDFは公開Snapshotの当日特徴量を保存済みRidgeへ入力し、12M・6Mのモデル上位10社、
既存Rule順位、相対Score、PER、PBR、ROEを1ページに表示する。相対Scoreは期待リターンではない。
JSONにはレポート日、推論基準日、Model Version/Run、SHA-256を残す。
同じ日を再実行した場合は同日のレポートだけを原子的に置換し、別日の履歴は残す。

## 3. 日次処理

`asset-poc daily`はパイプラインロック内で次を順に実行する。

1. DB内の最新UniverseからTOPIX 500相当watchlistを再構築
2. TDnetの前日までの未取得日を1回最大7日ずつ追随取得
3. Yahoo Finance株価を最終取得日との差に応じて1か月・3か月・2年取得
4. J-Quants Freeの12週間遅延対象日を補完取得
5. `price_clean_v2_dual_price`でrawを変更せず評価価格とリターン価格を分離
6. 価格・財務特徴量を再計算
7. Rule Rank 6M/12Mを再計算
8. データ品質検査
9. PASS時だけ公開SnapshotをAtomic更新
10. 最新公開特徴量へ6M/12Mモデルを推論
11. `run-daily.sh`が1ページPDF・JSONをOneDriveへコピー

`daily-report`は`daily`成功後だけ実行する。レポート生成またはDriveコピーに失敗しても、
公開済みデータは有効であり、原因解消後に`asset-poc daily-report`だけを再実行できる。
TDnet取得は日次へ統合済みだが、LLM構造化は含まない。`daily`だけでは新規TDnet原文が
定性特徴量になることはない。また、JPX Universe原本のネットワーク再取得も日次には含まれず、
DB内のUniverseを使ってwatchlistを作り直す。

日次処理は同一主キーへのupsertで、同じ日を再実行しても重複しない。外部取得Stepは最大3回
再試行し、最終失敗は`retry_queue`へ記録する。6時間以上残った`running` Batchは次回起動時に
`aborted`へ回収する。

### 日次確認

```bash
cd /path/to/asset-ai-adviser/poc
source .venv/bin/activate
asset-poc status
tail -n 100 logs/daily.log
```

画面では「比較・評価」タブでモデル順位と評価を確認する。データ充足の説明図は画面には出さず、
asset-poc generate-data-coverageでpoc/output/coverage/data-coverage-heatmap.pngへ保存する。
銘柄×月の上段は株価日足の件数を青の濃淡で示し、下段は決算開示日を赤丸で示す。
このため、日次で連続する価格データと、四半期・年度などのイベントデータを混同せず確認できる。
現在のPNGでは価格と決算を同じ座標へ重ね、右側に銘柄別の価格月カバレッジ（青棒）と
決算月カバレッジ（赤点）も表示する。カバレッジは対象期間中に1件以上データがあった月の割合である。

## 4. 過去データの収集

### 4.1 株価

新規銘柄や履歴不足銘柄を含め、Yahoo Financeが返す全期間を再取得する。

```bash
asset-poc collect-yahoo --period max
asset-poc analyze-price-quality
asset-poc publish
```

保存先は`secondary_prices`で、同一日・銘柄・ソースはupsertされる。rawは上書きクリーニングせず、
異常は`price_quality_events`と派生`model_price`で管理する。

### 4.2 財務

初月だけJ-Quants Standardを契約し、約10年の財務サマリーをローカルへ保存する。初回取得完了後は
Freeへ戻し、日々の適時開示はTDnetを主経路とする。

```bash
asset-poc backfill-financials \
  --min-periods 40 \
  --requests-per-minute 30
asset-poc publish
```

`--min-periods 40`は40件取得する指定ではない。既存開示日数が40未満の銘柄を再取得対象にする
閾値で、対象銘柄にはJ-Quants APIが返す全履歴を要求する。新規上場企業は正常取得後も40未満に
なり得る。全銘柄を再取得する場合だけ`--force`を使う。

### 4.3 TDnet原文

```bash
asset-poc collect-tdnet-date --date 2026-08-12
asset-poc collect-tdnet-date --date 2026-08-12 --code 7203
```

無料Web経路は直近約31日を主対象とする。それ以前の完全な長期履歴取得は現行実装では保証しない。
PDF・XBRL・抽出テキストとURL、取得日時、ハッシュを保存する。

### 4.4 LLM構造化

```bash
asset-poc structure-disclosures --limit 10
asset-poc evaluate-qualitative
asset-poc publish
```

LLMは未構造化文書がある場合だけAPIを使用する。構造化後に`publish`を実行すると、既存の定性
特徴量がRule Rankへ反映される。API費用を管理するため、日次自動処理ではなく週次または人手確認後を
推奨する。

### 4.5 過去Universe

現在は2026-07-31時点の492銘柄を過去へ固定している。過去月ごとの採用・除外銘柄、上場廃止銘柄を
含むUniverse履歴は未実装で、生存者バイアスが残る。モデルを正式採用する前の優先課題とする。

## 5. 学習モデルの定期更新

### 5.1 実行手順

日次処理が成功し、別のパイプラインが動いていない状態で実行する。

```bash
asset-poc backup
asset-poc build-training-dataset
asset-poc train-model --horizon all
asset-poc evaluate-model --horizon 6m
asset-poc evaluate-model --horizon 12m
```

`build-training-dataset`は、過去の各月時点で利用可能だった価格・財務だけから特徴量を再構築し、
翌取引日から6M/12M後のラベルを作る。`train-model`はRidgeを時系列分割で学習し、Rule Rankとの
比較、係数、テスト予測、最新順位をversion付き成果物として保存する。

学習中は`pipeline.lock`を保持するため、`daily`、`publish`、`backup`、他の学習コマンドを同時実行
しない。

### 5.2 現在のモデル管理

- 正式順位: `rule_rank_v6_unadjusted_valuation`
- 学習候補: `ridge_rank_v2_unadjusted_valuation`の6M・12M
- 学習成果物: `poc/output/models/<UTC run>/`
- DB登録: `trained_models`、`model_predictions`
- 画面: 6M/12Mが両方揃った最新runを「比較・評価」タブに表示

新しい学習runを作っても、メインのRule Rankは変わらない。一方、学習タブは最新の完全runを自動で
表示するため、再学習後は画面上のChallengerが更新される。

## 6. モデル改善と入れ替え方針

### 6.1 改善候補

優先順は次のとおりとする。

1. 過去Universeを導入し、生存者バイアスを削減
2. TOPIX超過・業種超過ラベルを追加
3. 売買コストとTurnoverを含む評価
4. 複数のWalk-forward窓で安定性を確認
5. RidgeとElastic Net、勾配Boostingを同一条件で比較
6. 業種・企業規模の偏りを制御
7. LLM定性特徴量あり/なしのAblation評価

複雑なモデルを先に導入せず、データと評価条件を改善してから比較する。

### 6.2 Champion昇格条件案

以下は運用ルール案であり、自動判定は未実装である。

- Point-in-Time検査と品質検査にFAILがない
- 6M・12Mそれぞれで12か月以上の完全な期間外テストがある
- 平均Rank ICと上位10%超過が現行Championを上回る
- Positive IC率が50%を超える
- Turnover増加を売買コスト込みで許容できる
- 特定の1期間・1業種だけでなく、複数期間・主要業種で改善する
- 係数またはSHAP等で説明可能で、異常な単一特徴量依存がない
- 過去Universeを使った評価でも改善が維持される

旧Ridgeは価格リーク判明により削除済みである。v2の再学習後も、過去Universe、コスト、複数窓評価が
未整備の間はChampionへ昇格させない。

### 6.3 入れ替え・ロールバック

モデルの自動昇格、承認状態、Championポインタ、Atomic切替CLIは未実装である。正式導入時は次を
追加する。

1. Model Registryに`challenger / approved / champion / retired`を保存
2. 6M・12Mを別々に承認
3. 評価結果と承認者、承認日時を記録
4. `champion.json`をAtomicに切り替え
5. 画面・ランキング生成はChampionポインタだけを参照
6. 問題時は直前のChampionへポインタを戻す

旧モデルは今回のように既知の情報リークが判明した場合は削除する。正常な将来モデルはdataset version、
model version、run時刻とともに保管する。

## 7. 再処理と保存方針

データ層ごとの扱いを固定する。

| 層 | 保存・削除方針 | 再処理 |
|---|---|---|
| raw原文 | 原則永久保存。修正・上書き・自動削除しない | 取得日時、URL、hashから再読込 |
| 正規化DB | 主キーupsert。誤データは削除せず品質イベントで無効化 | rawから再投入可能 |
| 特徴量・順位 | Version付き派生データ。旧Versionは採用停止後に整理可能 | `publish`で再計算 |
| 学習表・モデル | Dataset/Model Versionと評価結果を一緒に保存 | 同じVersion条件で再生成 |
| 公開Snapshot | 品質PASS版だけを公開。失敗時は直前正常版を維持 | `publish`でAtomic切替 |
| 日次レポート | 日付別に保存し、同日再実行だけ置換 | `daily-report --date YYYY-MM-DD` |

再処理の起点は次のように選ぶ。

1. 通信失敗・PC停止: `daily`を再実行し、watermarkからCatch-up
2. 取得ロジック変更: rawを残したまま正規化処理から再実行
3. クリーニング・特徴量変更: Versionを上げ、全期間の派生データを再生成
4. ランキング重み変更: Ranking Versionを上げ、旧順位と比較してから公開
5. モデル変更: 新runをChallengerとして保存し、自動でChampionへ切り替えない
6. レポート転送失敗: データ取得は再実行せず、`daily-report`だけ再実行

raw、DuckDBバックアップ、日次レポート履歴は自動削除しない。容量整理を行う場合も、対象は
`tmp/`、キャッシュ、失敗した未完成モデルrun、採用停止済み派生Versionに限定し、実行前に
バックアップと対象一覧を確認する。

## 8. 障害時の手順

### 日次処理が失敗した

```bash
pgrep -af asset-poc
tail -n 200 logs/daily.log
asset-poc daily
```

同じ処理はupsertされるため、原因解消後の再実行を基本とする。別プロセスが動いている場合は終了を
待ち、強制終了は最後の手段とする。

### 品質検査がFAILした

旧公開Snapshotは維持される。画面の「データ状態」と`data_quality_results`で原因を確認し、取得・
クリーニング・特徴量を直した後に次を実行する。

```bash
asset-poc publish
```

`publish`はネットワーク取得、TDnet取得、LLM構造化、学習を行わず、DB内の現状から特徴量、Rule Rank、
品質検査、公開Snapshotだけを更新する。

### バックフィル・学習が中断した

ロック保有プロセスが終了すればOSロックは解放される。raw・DBはupsertで、学習表はdataset version
単位で再作成できるため、同じコマンドを再実行する。完成していないモデルrunは比較・評価タブに表示されない。

### DBを復元する

Streamlitとタスクを止め、現DBを別名退避し、`data/backups/`の検証済みバックアップをコピーする。
復元後は`asset-poc publish`で品質検査し、画面を再公開する。自動復元CLIはない。

## 9. 現在の未自動化項目

- 月次学習データ再構築と再学習のスケジュール登録
- LLM構造化の費用上限付き定期実行
- 過去Universe取得
- TOPIX・業種超過ラベル
- 複数Walk-forward評価と売買コスト
- Model Registry、承認、Champion切替、ロールバック
- 異常時のメール・チャット通知

これらを実装するまでは、日次Rule Rankを安定運用し、学習モデルは画面上の比較候補として扱う。
既定のOneDrive出力先は`run-daily.sh`に設定済みで、`REPORT_OUTPUT_DIR`により変更できる。
