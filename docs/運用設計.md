# 定期起動・リカバリ運用設計（PoC v1）

## 1. 目的と前提

TOPIX Core30・Large70・Mid400相当の約500社について、株価、取得済み決算、特徴量、
6M/12M順位をローカルで継続更新する。外部サービスは基本無料の範囲を使用し、LLMは
この運用経路には含めない。

WindowsタスクスケジューラからWSL上のPoCを起動する。PC停止・スリープ中に予定時刻を
過ぎた場合は `StartWhenAvailable` で復帰後に実行する。

## 2. 定期処理

| 処理 | 頻度 | 入力・取得範囲 | 失敗時 |
|---|---:|---|---|
| 日次Batch | 毎営業日を含む毎日 19:30 | 下記Step一式 | 次回起動時にも再実行可能 |
| TDnet決算開示 | 日次 | 前日までの未取得日、直近30日を上限にCatch-up | 最大3回再試行 |
| Yahoo株価 | 日次 | watermarkとの差に応じ1か月・3か月・2年 | 最大3回再試行 |
| J-Quants決算差分 | 日次 | 12週遅延の対象日、未処理を最大7日Catch-up | 最大3回再試行 |
| 特徴量・順位 | 日次 | DB内の最新有効データ | 冪等再計算 |
| 品質検査・公開 | 日次 | 最新順位と履歴 | FAIL時は公開しない |
| DuckDBバックアップ | 毎週日曜 20:30 | `data/poc.duckdb` | 次回週次または手動実行 |
| 決算初回Backfill | 手動 | 指定した開示日数未満の対象銘柄 | 銘柄単位で再開 |

J-Quants Free planの決算は12週間遅延である。TDnetの日付指定取得と本文抽出は日次処理へ
統合済みで、直近開示を補う。LLM構造化はAPI費用を伴うため日次処理へ統合せず、手動または
費用上限付きの別処理とする。月次学習データ再構築とモデル再学習も日次処理には含めない。

## 3. Batchと状態管理

1回の `asset-poc daily` にUUIDの `batch_run_id` を発行する。`batch_runs` に全体状態、
`batch_steps` にStepと試行回数を記録する。状態は `running / succeeded / failed / aborted`
で、6時間を超えた `running` は次回起動時に `aborted` へ回収する。

外部取得Stepは最大3回再試行し、最終失敗を `retry_queue` に残す。取得・特徴量・順位の
保存は同じ主キーへのupsertであるため、同じ日・同じデータの再実行で重複しない。

`source_watermarks` は次を保持する。

- `yahoo_finance / daily_prices`: DBに保存できた最新取引日
- `jquants_v2 / financial_summary_date`: 正常取得した最後の対象日
- `tdnet_free_web / disclosure_date`: 正常取得した最後のTDnet対象日

watermarkは保存成功後だけ進める。J-Quants決算の未処理日が多い場合は1回に7日まで処理し、
次回BatchへCatch-upを継続する。

## 4. 排他と障害復旧

`data/pipeline.lock` をOSファイルロックし、日次処理・バックアップの同時実行を禁止する。
重複起動は異常終了ではなく `skipped` として扱う。プロセス強制終了時にはOSがロックを
解放するため、lockファイルが残っていても次回起動できる。

| 障害 | 自動動作 | 手動対応 |
|---|---|---|
| 一時的な通信・HTTP失敗 | Stepを最大3回再試行 | 次回 `daily` でもupsert再実行 |
| PC停止・スリープ | 復帰後にタスク起動 | タスク履歴を確認 |
| Batch途中終了 | stale状態回収、watermarkからCatch-up | `asset-poc daily` |
| 品質検査FAIL | 新Snapshotを公開せず旧版を維持 | `data_quality_results`を確認 |
| 画面表示中の更新 | Rule Rankは公開Parquet、学習タブはモデル成果物を参照 | 対応不要 |
| DuckDB破損 | 週次バックアップを使用 | 後述の復元手順 |
| 誤ったランキング方式 | 公開済み旧世代は残る | `latest.json`を旧世代へ切替可能 |

## 5. 品質ゲート

次の必須検査がすべてPASSの場合だけSnapshotを公開する。

- 対象銘柄数: 450〜550
- 株価カバレッジ: 98%以上
- 最新株価日: 実行日から7日以内
- 株価主キー重複: 0
- OHLC・出来高不正: 0
- ランキング件数: 対象銘柄数と一致
- 6M/12M順位・Score範囲: 不正0件
- 説明可能性JSON: 不正0件

決算カバレッジ80%未満はPoC中はWARNとし、価格中心・低Confidenceで順位を作れるため
公開を止めない。閾値と結果は `data_quality_results` に保存する。

## 6. Atomic公開

画面はDuckDBを直接読まない。品質検査後、次を
`data/published/runs/<batch_run_id>/` へParquetで書く。

- `ranking_latest.parquet`
- `price_history.parquet`
- `financial_history.parquet`
- `data_coverage.parquet`
- `price_quality_events.parquet`
- `qualitative_latest.parquet`
- `batch_runs.parquet`, `batch_steps.parquet`, `data_quality.parquet`

全ファイル完成後、`data/published/latest.json` を `os.replace` でAtomicに切り替える。
更新中断や品質FAIL時はポインタを変更しないため、画面には直前の正常版が表示され続ける。

## 7. 導入・コマンド

PoC内で初回公開と確認を行う。

```bash
cd /mnt/c/Users/ShunK/works/asset-ai-adviser/poc
source .venv/bin/activate
asset-poc publish
asset-poc status
streamlit run src/asset_poc/app.py
```

Windows PowerShellで定期タスクを登録する。

```powershell
cd C:\Users\ShunK\works\asset-ai-adviser\poc
powershell -ExecutionPolicy Bypass -File .\scripts\register-tasks.ps1
```

WSL Distribution名を指定する場合は `-WslDistribution Ubuntu` を加える。タスク名は
`AssetAIAdviser-Daily` と `AssetAIAdviser-Backup`。ログは `poc/logs/` に出力する。

手動運用コマンド:

```bash
asset-poc daily                 # 通常の日次更新
asset-poc daily --skip-network  # ローカルデータだけで再計算・検査・公開
asset-poc backup                # 手動バックアップ
asset-poc backfill-financials --min-periods 40 --requests-per-minute 30
```

`--min-periods` は取得件数ではない。既存の開示日数が指定値未満の銘柄を再取得対象にする
閾値で、対象銘柄についてJ-Quants APIが返す全履歴を取得する。上場間もない企業は正常取得後も
指定値未満になり得る。バックフィル中はパイプラインロックを保持するため、`publish`、`daily`、
`backup`、DuckDBへ接続する集計を同時実行しない。

## 8. バックアップ復元

`asset-poc backup` はCHECKPOINT後に `data/backups/poc-YYYYMMDD-HHMMSS.duckdb` と
SHA-256付きJSONを作る。PoCでは誤操作防止のため自動復元CLIは設けない。

復元時はStreamlitと定期タスクを止め、現DBを別名で退避してから選択したバックアップを
`data/poc.duckdb` へコピーする。その後 `asset-poc publish` で品質検査し、Snapshotを
再公開する。バックアップを上書きせず、復元前DBを残すこと。

## 9. 監視の最低条件

日次で `logs/daily.log` と画面の「データ状態」を確認する。次を異常として扱う。

- 最終成功Batchが2日以上ない
- 品質結果にFAILがある
- `retry_queue` にpendingが残る
- 最新株価日が7日超
- 決算カバレッジが想定より低下する

PoC段階ではメール通知を入れず、Batch履歴・ログ・画面表示までを実装範囲とする。
